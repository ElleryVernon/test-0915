# PDF 근거와 원본 표시

2026-09-17. 사용자 교재의 실제 저장된 인용문과 PDF 20–21쪽으로 확인했다.

## 원인

단일 citation 문자열에 본문, 수식의 일부 기호, 그림 라벨, 캡션이 섞였다. 1,200자 청크는 700자 이전의 문단 경계를 무시했고, 최대 세 청크를 이어 붙여 3,464자의 근거가 표시됐다. 공백을 줄이거나 AI로 문장을 다듬어도 사라진 화살표·분수·위치를 복원하지 못한다.

## 이번 구현

- 원본 PDF와 저장된 인용문을 변경하지 않는다. 서술형과 문제풀이의 공통 Citation에서 원본 페이지와 텍스트 발췌를 나눈다. 서술형 힌트에서도 같은 근거를 열 수 있다.
- 전체 근거를 펼치면 PDF의 해당 페이지만 카드 안에서 렌더링한다. 벡터 도식, 이미지, 수식이 함께 보인다. 텍스트 보기에서는 연속된 기호 조각만 별도 접힘 영역으로 표시하고 원문 자체는 보존한다.
- 소유권을 확인하는 기존 upload API에 `pages` 선택을 추가했다. PDFium이 선택한 원본 페이지만 복사한다. 최대 12쪽, 오름차순, 중복·범위 밖·비PDF 요청 거부. 원본 파일과 인용문은 수정하지 않는다. ETag는 원본 해시와 페이지 선택에 따라 구분한다.
- 원본 보기는 citation 위치와 페이지 경계로 결정한 페이지만 표시한다. 원문 PDF 텍스트와 인용문의 긴 연속 구간을 대조하고 유일하게 일치하는 구간에 브랜드 주황색을 덧씌운다. `--source-highlight` 토큰은 `--brand`의 32% 불투명도를 사용한다. 문서 전체 키워드 검색이나 유사도만으로 강조하지 않는다. 부호·숫자는 유지하고 공백·유니코드 호환 글자만 정규화한다.
- 캔버스 위 강조는 PDF 텍스트의 실제 좌표를 사용한다. 부분 텍스트는 글꼴 측정으로 범위를 제한한다. 회전 글자나 매칭되지 않은 손상 기호는 임의 강조하지 않는다. 추출 좌표가 없는 스캔 이미지의 정확한 부분 강조는 아직 지원하지 않는다.
- 새 생성의 evidence 블록은 짧은 문단도 경계로 사용하고 긴 문단은 문장 경계를 우선한다. AI가 원문을 다시 쓰지 않고 ID로 고르는 계약은 유지한다. 생성 버전 quiz/cards 2.8.0, essay 2.11.0. 기존 문항 재생성이나 새 버전의 유료 품질 평가를 했다는 뜻은 아니다.

## 실제 측정

로컬 QA 소유의 Lehninger 6장: 전체 48쪽, 1,573,912바이트에서 근거 20–21쪽, 162,608바이트로 전송량이 약 89.7% 줄었다. 선택 PDF 텍스트는 원본 해당 페이지의 PDF.js 텍스트와 동일했다. 20쪽에서 104개, 21쪽에서 14개 텍스트 강조 구간을 찾았다. 구간 수는 과학적 근거 충족률을 뜻하지 않는다. API 잘못된 페이지 요청은 400을 반환했다. 재현 스크립트와 결과는 `.unlazy/citation-evidence/audit.ts`, `audit.json`에 있다.

## 더 나은 저장·검색 구조

장기적으로 `원본 파일 + 문서 블록 + 근거 참조 + 해설`을 구분해야 한다. 블록마다 `sourceHash`, `parserVersion`, `page`, `kind`(본문/표/그림/수식), 좌표, 원문 오프셋, 캡션 연결을 보존하고, 문항은 블록 ID와 인용 범위만 참조하는 방식이다. 한국어 풀이·요약은 원문 인용과 별도 필드로 저장하고 해당 블록을 근거로 검증한다. 이는 구조 설계 제안이며 이번에 전체 DB를 마이그레이션하거나 교재를 재수집한 것은 아니다.

| 후보 | 공식 문서에서 확인한 기능 | 이 프로젝트에서의 판단 |
|---|---|---|
| [DoclingDocument](https://docling-project.github.io/docling/concepts/docling_document/) + [HybridChunker](https://docling-project.github.io/docling/concepts/chunking/) | 문서 요소·구조를 유지하고 구조와 토큰 길이를 함께 고려한 청크 생성 | 로컬 비교 후보. 교재 정확도·메모리·처리 시간은 아직 측정하지 않았다. |
| [Google Document AI Layout Parser](https://docs.cloud.google.com/document-ai/docs/layout-parse-chunk) | 제목·본문·표·그림의 계층과 문맥을 유지하는 청크. 모델 버전에 따라 시각 요소 설명 지원 | 기존 GCP와 연결하기 쉬운 후보. 표·그림 설명도 생성 결과이므로 원본 대조가 필요하다. |
| [Azure Document Intelligence Layout](https://learn.microsoft.com/en-us/azure/ai-services/document-intelligence/prebuilt/layout?view=doc-intel-4.0.0) | 문단과 그림의 페이지·polygon·span·caption 연결 | 위치 기반 인용과 강조의 비교 기준. 추가 외부 서비스를 실제 연결하지 않았다. |

세 파서를 이 교재에서 직접 비교하지 않았으므로 가장 정확하거나 빠르다고 순위를 매기지 않았다. 비교 시 본문 읽기 순서, 수식 부호, 그림-캡션 연결, 참조 좌표 정확도, 페이지당 처리 시간과 비용을 같은 PDF 페이지로 측정해야 한다. 현재 구현의 전송량 개선을 파서의 이해도 개선으로 해석하지 않는다.

## 검증 범위

실제 로컬 QA 서술형 화면의 힌트 → 공통 근거 → 원본 보기에서 390×844 모바일 표시, 근거 2쪽 전환, 150% 확대, 118개 강조 영역, 가로 넘침 없음을 확인했다. 공유 컴포넌트는 채점 결과에도 적용된다. 새 채점 요청 1회는 기존 grade 2.9.3 검수에서 거절됐다. 따라서 새 채점 성공을 근거로 이 화면을 검증했다고 주장하지 않는다. 채점 품질 전체 게이트 G3/G8은 계속 미완료다.
